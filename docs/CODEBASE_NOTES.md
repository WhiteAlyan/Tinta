# Tinta — Codebase Notes

Historical context for the codebase, extracted from the source
files by `scripts/extract_codebase_notes.py`.

**What happened to the original notes, honestly:** this file was
once generated by stripping ~800 comment blocks out of the sources
into this document. The generated file was then lost down to its
intro stub, and with no git history the block texts became
unrecoverable — every one-line `// Historical context:` header in
the sources was left pointing at an anchor that no longer existed
(the external code review counted 849 such dead letters).

**The contract now:** anchors are per-FILE and stable
(`docs/CODEBASE_NOTES.md#jsgrammarmodal-js`), not per-line-range,
so ordinary edits can never kill them again. This file is
regenerated with `python3 scripts/extract_codebase_notes.py` — a
non-destructive pass that reads the comment blocks currently in
the sources and never modifies them. `--verify` fails loudly if
any cross-reference in the codebase stops resolving. Sections for
files whose historical blocks were lost carry a note saying so;
their surviving context is the section's current blocks and the
per-batch `FIXES-ROADMAP-*.md` documents at the repo root.

## js/autoBackupName.js <a id="jsautobackupname-js"></a>

### Lines 1–15

```
Roadmap #9 — pure naming/rotation logic for the folder auto-backup,
split out of autoBackup.js so the smoketest can exercise it in Node
without importing the File-System-Access side of the module. Nothing
here touches a handle, a store, or the DOM: strings in, strings out.

The auto-backup used to write ONE fixed-name .tinta per project: every
save overwrote it, so a mistake made today replaced yesterday's good
copy with today's bad one — a mirror, not a safety net. Backups now
carry a local-DATE stamp in the filename: the same day's saves rewrite
the same dated file (no file spam from the save debounce), and after
each successful write the folder is rotated down to the newest
AUTOBACKUP_KEEP dated files for that project. Five dates is a work
week of history. Only files matching the exact naming pattern are ever
selected for deletion — manual exports and anything else in the folder
are untouched.
```

### Lines 32–39

```
Pure selection logic — unit-tested in autoBackup-name.smoketest.mjs.
Given every filename in the folder and the current project's base name
(the export filename minus .tinta), return the auto-backup files to
DELETE: this project's dated backups, oldest first, everything past
`keep`. Anything not matching the exact
`<base>-autosave-YYYY-MM-DD.tinta` shape is never selected — a renamed
project's old backups, manual exports, and unrelated files in the
folder are all invisible to this function.
```

## js/drawer.js <a id="jsdrawer-js"></a>

### Lines 2–13

```

P2-10 documentation — drawer.js and modal.js implement parallel
open/close logic for two different overlay concepts. See the
equivalent header comment at modal.js:1-19 for the full note.
Briefly: modal.js handles blocking overlays that dim the manuscript
(Library, Settings, etc.); drawer.js (this file) handles the
non-blocking inspector that doesn't dim. Both files implement
outside-click + teardown-with-innerHTML-clear + class-toggle-for-
"open" patterns independently. A shared DismissableOverlay helper
would unify them; deferred because both files are large and the
semantic differences (modal blocks via backdrop; drawer doesn't)
would need to be preserved, not just dedup'd.
```

### Lines 510–527

```
Renders one label/value row in a drawer's meta block.

SECURITY: this used to funnel every value through raw(), which meant any
ordinary string handed to it became live markup. Rule-node metadata
(Category/Rank/Cost/…) is plain project data, and project data arrives
from .tinta imports — so a stored value like `<img src=x onerror=…>`
executed the moment the drawer opened. The fix is to interpolate the
value through html`` and let the tagged template decide: SafeHtml (built
by a caller's own html`` literal) passes through verbatim, arrays of
SafeHtml are joined, and anything else is escaped as text. raw() is now
only ever called at audited trust boundaries, never here.

Interpolating instead of hand-joining also fixes the Tags row: an array
of SafeHtml chips used to stringify to "[object Object],[object Object]"
because the old `'value' in valueHtml` check didn't match arrays.

Callers must therefore pass RAW values, not escapeHtml()'d ones —
pre-escaping now double-escapes ("&" would render as "&amp;").
```

## js/recoveryStore.js <a id="jsrecoverystore-js"></a>

### Lines 1–27

```
P2-7 fix — IndexedDB-backed recovery snapshot for quota-exceeded saves.

Problem this closes: when localStorage.setItem throws a quota error
in store-core.js's writeToLocalStorage, the in-memory _db has
mutations that don't reach disk. The retry timer retries the SAME
payload that just failed — if the db is over quota because of
accumulated snapshots/images, retrying won't help until the writer
manually trims. If the writer closes the tab before a retry
succeeds, the in-memory state is lost.

The natural fix — write the unsaved state to a separate localStorage
key — does NOT work because localStorage quota is shared across
keys. A write that fails for the main `tinta:db` key will also fail
for `tinta:db:unsaved:...` with the same payload.

IndexedDB has a much higher quota (~50MB+ per origin vs localStorage's

payload fails to land in localStorage. On next boot, we check for a
recovery snapshot and surface a non-blocking toast offering to
restore the lost changes. If the snapshot's rev is <= the disk db's
rev (because the retry timer eventually succeeded before the tab
closed), the snapshot is stale and is silently cleared.

The snapshot is the FULL in-memory _db serialized as JSON. We don't
try to diff against the disk db — that's complex and the typical
recovery case is "all my work since the last successful save is
gone", which is the full db anyway.

```
── hostile-input hardening (resource limits) ───────────────────────────

.tinta files are external input — this app reads them from disk with no
server in between to pre-validate anything. parseZipEntries() below is a
hand-rolled zip reader (kept small on purpose, to avoid a dependency),
which means it trusts a lot of archive-controlled offsets and sizes by
construction. Every one of those numbers now gets checked against what's
actually in the file before anything reads from it, and bounded before
any bytes get copied. Two attack shapes this specifically defends
against:
  - a whole-file DoS: handing the tab a file too large to safely read
    into memory at all (checked via file.size, before any read happens)
  - a duplication DoS: a SMALL file whose central directory claims many
    entries that all overlap the same region, so each entry individually
    fits inside the file, but their declared sizes SUM to far more data
    than the file actually contains — copying every one of them would
    multiply the file's real size by however many entries are listed
None of these numbers are exact spec limits (except the end-of-central-
directory search window, which is) — they're generous ceilings for what
a real writing project could plausibly need, picked to leave headroom
while still bounding worst-case memory/CPU use to something a browser
tab survives.
